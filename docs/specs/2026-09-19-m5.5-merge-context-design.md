# M5.5 — merge review and the contextual check, the two cold paths

**Status:** designed, on branch `m5.5-merge-context`
**Date:** 2026-09-19
**Parent:** `docs/specs/2026-09-17-oarfish-design.md` — milestone M5.5 in §11, mechanism in §5.6 and §5.8

---

## 1. What this milestone is for

§11 gives M5.5 the contract *a close pair is judged once, and a flagged burst resolves
to `wake_someone`*. Both halves are cold-path Jev passes that M5 named and deferred, and
together they finish the decision layer: after M5.5 every value §5.9's routing table
reads is a value something actually produces.

That is the point of the milestone. M5 implemented `route()` exactly as §5.9 specifies
and then had nothing to feed it — `wake_someone` arrives only from the contextual check,
so the function was reachable only from its own tests. M5.5 is what connects it.

The two halves are independent of each other and meet only at the engine. They share
this document because they share everything that matters about their shape: the cost
model, the `Decide` seam, the key discipline, and the rule that a decision is recorded
before it is trusted.

## 2. Boundaries

| In (M5.5) | Out |
|---|---|
| Merge review (§5.6) and the `merges` keyspace | ntfy delivery — M6, [#24](https://github.com/Toby-Faucher/oarfish/issues/24) |
| The contextual check (§5.8) and its question set | Rendering merges or correlation on the board — M6 |
| Alias resolution on the engine's input | Operator corrections and the `corrections` keyspace — M6 |
| `wake_someone` wired into `route()` | Window persistence — unscheduled, §5.7 says in memory |
| Pending raises for flagged templates | Other delivery channels |

**The page lane stays undelivered.** M5.5 makes `Lane::Page` *reachable* — a burst can
now route to it with a real `wake_someone` behind it — but nothing is on the other side
until M6. This is deliberate and it is the whole content of issue #24: the signal and
its delivery are separable, and landing the signal first means M6 builds against a value
it can observe rather than one it has to simulate.

## 3. The cost model

Both halves sit on the cold paths §1's rate table already names.

| Rate | What | Cached against |
|---|---|---|
| Per close pair | Merge review | the canonical pair key, §5 |
| Per burst, flagged only | Contextual check | not cached, by design |

Merge review caches **both answers**. A `no, these are different` is as expensive to
re-derive as a `yes` and far more common, so storing only the merges would re-ask every
rejected pair on every restart — turning a per-pair cost into a per-restart-per-pair
cost, which is the exact failure the rate table exists to prevent.

The contextual check is uncached because its answer is about a burst, not a template.
Caching it would mean serving a judgement about Tuesday's incident during Thursday's.

**What this adds to the every-line path: one `HashMap` lookup.** Alias resolution (§6)
runs in the engine before it touches windows. Pure Rust, no network, no disk — invariant
2 holds. Candidate scanning (§4) runs only when a genuinely new cluster appears, which
§5.6 puts at perhaps a dozen times a day.

## 4. Finding candidates — a read-only query on `oarfish-drain`

§5.6 says *any new template structurally close to an existing one*, and defines neither
"close" nor where the search lives. Both need answering.

**Where.** `Pipeline` owns the `Drain` and is the only thing that knows a cluster is new
— `Drain::train` takes `&mut self`, so there is exactly one consumer by construction.
The cluster table lives there and nowhere else, so the search lives there too.

**What "close" means, and why it cannot reuse the tree.** The motivating case in §5.6 is
*one real event split in two because an optional field changed the token count*. Drain's
first tree level **is** token count. Two templates differing by an optional field are
therefore in different subtrees and share no parent node, so any candidate search built
on the tree's own structure would systematically miss the exact case §5.6 exists to
repair. The search has to cross token counts on purpose.

`oarfish-drain` gains a token-count index (`BTreeMap<usize, Vec<u64>>`, maintained
alongside the existing table) and one read-only query:

```rust
pub fn neighbours(&self, seq: u64, query: &NeighbourQuery) -> Vec<Candidate>
```

- **Count window:** ±2 tokens. Wide enough for an optional field or a short suffix,
  narrow enough that the index turns an O(n) table walk into a handful of bucket reads.
- **Score:** Jaccard over token multisets.
- **Referral band:** `[0.65, 1.0]`. The floor is a tuning choice and is configuration.
  *(Revised 2026-09-22. This had a ceiling at 0.90, on the premise that a pair
  scoring there would already be one cluster. That premise is false: Jaccard ignores
  position, and Drain never compares across token counts or across tree paths. An
  optional eleventh field scores 10/11 ≈ 0.909, and a word varying at token 2 of 20
  scores 19/21 ≈ 0.905. Both are split, and both are the closest over-splits of all.
  The M2 spec's own "word-varying early position never meets in the tree" is the
  same fact.)*

This is an **oarfish addition, not part of the drain3 port**, and its doc comment says
so. It is read-only and touches no clustering decision, so the snapshot equivalence
against drain3 that M2 established is unaffected — which is the property that makes
adding it to this crate acceptable rather than a violation of what the crate is for.

## 5. Merge review — a second consumer of the `Decide` seam

`oarfish-store` gains `Merges`, built to the shape `Judge` already proved: a bounded
queue, a background task, cache-aside over its keyspace, and the provider behind
`Decide` so production judges through the Jev client and tests judge through the
existing fake — no network, no billing, chosen answers. A dropped enqueue is harmless
for the same reason it is in `Judge`: the next new template refers the pair again.

One question, per §5.6, a `noul`: *do these describe the same event type?*

### The key

```text
id_lo (32B) ++ id_hi (32B) ++ questions_hash (16B) ++ bundle_hash (32B) ++ resolved_model_id
```

Canonically ordered, so `(A, B)` and `(B, A)` are one row and the pair is asked once
rather than twice.

The trailing three components are the discipline M4 §4 established and commit `37f0115`
corrected: a decision is valid only for the question that produced it, the bundle that
masked its templates, and the model build that answered. `bundle_hash` earns its place
for precisely M4's reason — `TemplateId::of` hashes masked text, so two different raw
lines can carry the same id under different bundles, and without the bundle component
the store could serve one pair's decision for another's.

The stakes here are higher than for a verdict, which is why the full discipline applies
rather than a cheaper key. Invariant 4 names the danger by name: a wrong merge *silently
deletes the alarm*. A stale merge decision served after a bundle edit is exactly that
failure, arriving quietly.

### Direction: the lower id always wins

The alias points from the lexicographically greater `TemplateId` to the lesser.

Semantically this is arbitrary, which is fine — both templates name the same event, so
there is no meaningful survivor to choose. What it buys is a structural property:
**every alias points strictly downward, so chains terminate and cycles are
unrepresentable.** `B -> A` and `C -> B` resolve to `A` by iteration, and no sequence of
merge decisions can construct a loop for the resolver to spin on. The resolver still
caps its iterations, but the cap is a backstop rather than the mechanism.

`Drain`'s `seq` cannot do this job even though "older cluster wins" reads better: `seq`
is documented as never persisted and renumbered on every restart, so an alias built on
it would not survive one.

## 6. Applying a merge — alias resolution in the engine

The repair has to take effect somewhere, and rewriting `TemplateId`s is not available:
their stability is a proptest invariant, and folding Drain's clusters together would
mutate the table from outside and be irreversible once lines had been absorbed.

Instead the engine resolves through the alias before it touches anything:

```text
pipeline -> EngineInput { template_id: B, .. }
                            |
                     resolve via `merges`
                            v
                         A            windows, dedupe and verdict lookup all key on A
```

Both templates then feed **one window and one alarm**. That is the actual repair — two
halves of a split event each see half the rate, and neither trips a threshold tuned for
the whole. Resolving only the verdict lookup would save a redundant judgement and leave
the over-split in place, which is the thing §5.6 is for.

Nothing is rewritten and no history is lost, so a bad merge is undone by deleting one
row. Given invariant 4's warning, being able to reverse a merge cheaply is worth more
than the tidiness of a real fold.

The alias table is read per line, so it is held in memory — loaded at startup from the
keyspace, updated when a decision lands — and never read from fjall on the hot path.

## 7. The contextual check — pending raises

The check lives in `oarfish-engine`: it needs window stats and open alarms, and invariant
5 keeps question policy out of `oarfish-jev`. Its three questions are §5.8's, in their own
set — `matters_now`, `correlates_with`, `wake_someone` — separate from the static six, so
adding them cannot move `questions_hash` and invalidate the verdict table.

### Surfacing decides before, not after

§5.8 requires that the engine never block on the check, and §5.9 gives `Lane::Record` the
meaning *record, no surface*. Together those rule out raising first and re-routing on the
answer: a `matters_now` of 0.2 arriving two seconds later would mean pulling an alarm back
off a screen someone may already be reading. **Nothing that has surfaced is ever
withdrawn.**

So the raise is what waits, not the engine:

```text
t+0.0   window trips, template flagged `contextual`
        capture host-scoped, bounded snapshot from `open`
        spawn the check, mark the key in-flight
        -> engine loop continues; nothing surfaces yet
t+0.3   more events on the key      -> window keeps bumping as normal
t+1.4   answer returns on the mpsc branch
        re-validate the snapshot
        matters_now below threshold -> Lane::Record, never surfaces
        otherwise                   -> raise into route(wake_someone)
```

`matters_now`'s threshold is configuration on `EngineConfig`, beside the
`actionable_threshold` the raise gate already reads. `route()`'s own cutoffs stay where
§5.9 put them: they are the routing table, not a tuning knob.

The engine's `select!` gains a third branch for returning answers. The loop itself never
awaits a Jev call; only the one raise is deferred.

**Failure raises rather than swallows.** An error or a timeout raises at `Dashboard` —
`route(None)`, exactly the M5 behaviour. A check that cannot answer must not be able to
suppress an alarm that the window already decided was worth raising; the safe direction
under uncertainty is toward the board, never toward silence.

### State, and why there is no cycle

The engine builds the snapshot from its own `open` map. It is the sole writer, so no lock
is involved and `core::Snapshot` — which exists to share the set with the board — is not
on this path. The capture is host-scoped and bounded to fit the token budget, and carries
what §5.8 lists: id, template id, severity, host, opened-at, one template excerpt. It is
persisted verbatim in the decision record, so the correlation is replayable.

`correlates_with` is a `choice` over the ids in that snapshot plus `none`, so the question
cannot name an alarm the model was never shown.

The check depends on a read-only `OpenAlarmView` trait rather than on the state machine.
That is what §5.8 asks for and it is also what lets the routing tests hand it chosen
snapshots instead of driving a whole engine to produce one.

**Re-validation on apply.** A Jev call is not instantaneous and `DelayQueue` auto-clear
runs independently, so the alarm named by `correlates_with` may have cleared during the
round trip. On apply the engine re-checks it and treats a vanished alarm as `none`. Data
flows one way per evaluation — committed state, then check, then answer, then mutation —
so feedback happens across bursts, which is the system tracking an incident, and never
within one.

## 8. Decision records

Both passes write a `DecisionRecord` before their answer is trusted, as M4 §8 requires.
Merge review's is keyed by the pair; the contextual check's by `Ulid`, since there is no
stable key for a burst.

This is not bookkeeping. *Why did this wake me three weeks ago* has to stay answerable,
and after M5.5 the honest answer to that question can be "because a contextual check
scored `wake_someone` at 0.94 against this snapshot of open alarms" — which is only true
if the snapshot was stored.

## 9. Testing and acceptance

| Property | Test |
|---|---|
| Candidates cross token counts | A pair differing by an optional field is referred; `wiremock` sees the request |
| High-scoring splits are referred | An optional eleventh field (≈ 0.909), an early varying word (≈ 0.905) and a reordering (1.0) are each referred |
| A pair is judged once | A second sighting fires **zero** further requests, on request count |
| A `no` is cached too | A rejected pair is not re-asked after a restart |
| Re-judge on change | A changed question, bundle or resolved model each miss the key |
| Merges repair the split | Two aliased templates share one window and raise one alarm |
| Aliases terminate | `proptest`: resolution always halts and never cycles, over generated decision sets |
| A merge is reversible | Deleting the row restores two independent templates |
| Flagged only | An unflagged template never reaches the check, on request count |
| Nothing surfaces early | No `AlarmChange` is published while a check is in flight |
| Confidence routes | Chosen `0.94` pages; chosen `0.61` does not |
| Failure raises | A 500 and a timeout each raise at `Dashboard` |
| Correlation re-validates | An alarm cleared mid-flight resolves to `none` |
| **Acceptance** | Two integration tests: a close pair is judged once; a flagged burst resolves to `wake_someone` and lands in `Lane::Page` |
